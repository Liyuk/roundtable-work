# Chief：围绕目标持续工作的循环

状态：用户意图与候选设计 · 2026-11-10。用户所说的是 **Chief**。Chief 是承担观察、判断、决策、沟通、委派、记忆召回和继续推进的角色；宿主是提供 session、计时、进程及通信等能力的运行环境。两者在具体实现中可以处于同一个系统，不应把 Chief 简化为只转发消息的外壳。

## 人与 Chief 如何分工

人主要表达要做什么、验收标准、重要约束和授权；可以随时提供新信息、纠偏、暂停和验收。Chief 在给定目标与授权内自主选择可逆的执行细节、分工、工作顺序和常规方案：低风险选择使用合理默认，记录依据并继续。用户的使用偏好是多数情况下接受 AI 的建议，发现不对劲时介入；这不是对任何外部账户、操作或高影响行为的无限授权。

不因为每一个不确定点都停下来：先查现有资料和记忆，比较合理选项；可低成本撤销的选择先做并记录。若关键目标或验收存在无法合理判断的歧义、需要新权限、涉及不可逆或超出预授权的行为，提出具体问题并继续其他可做工作。用户后续修正始终优先于旧假设，并触发受影响工作复核。

## 循环的真实含义

```text
目标、验收、范围和授权
        ↓
Chief 被输入 / 事件 / 定时唤醒
        ↓
观察工单、子任务、环境与用户新消息
        ↓
主动召回相关记忆 → 判断缺口、优先级和下一步
        ↓
自己决策 / 委派执行 / 等待结果 / 请求必要决策
        ↓
审查证据、验收阶段产物、吸收反馈 → 继续循环
```

“无限循环”表达持续持有未完成目标，不意味着持续占用模型或无条件重试。Chief 每轮必须产生可验证行动、可用结果、合理等待条件或明确停止原因。没有工作时可休眠；当任务结果、外部事件或设置的时间到来时，由具备相应能力的宿主唤醒。达到目标、被取消、授权失效、预算耗尽或连续无进展时按实际原因结束或暂停。提示词无法单独保证空闲后的唤醒和重启恢复，必须实测宿主能力。

## 等待任意 Agent

Chief 可将工作交给另一个 session、宿主原生子代理、命令行 Agent、服务或人；谁执行和哪个 harness 不是任务语义的前提。一次委派需要目标版本、责任人或执行实体、任务内容、授权、工作区、验收、产物位置和结果回送路径。按宿主实际能力记录已提交、已送达、已领取、运行中、结果与失败；不凭聊天文本假定执行发生。

等待某个 Agent 时，Chief 订阅该任务的结果、问题或失败；允许其他不冲突工作继续。不必忙等、不将任务尚未结束当作正在消耗算力。结果到达后复核目标版本和证据，再决定交付、独立验收、返修、改派或继续。若宿主只支持前台等待，则记录此限制；若支持结束回合后通知，需在实际宿主验证。对失败或结果未知的外部动作先核对，再决定是否重试。

## 多 session：为什么分开

多角色主要提供**上下文隔离、独立视角和阶段验证**。例如执行 session 专注改动，审查 session 从目标、变更和证据重新判断，降低只沿着作者思路走的风险；角色人设让人容易理解职责，但身份名称或换模型并不自动保证质量和独立性。

隔离的代价是上下文可能损失：设计原因、限制、用户的新要求或失败过程可能未被带到下一个 session。使用结构化交接卡传递目标与版本、原始需求链接、任务范围、重要决定及其依据、产物和实际检查、未完成项、权限、冲突和待回答问题；保留原始记录以供下钻，而非复制完整对话。检查消息被送达、读取并应用，不能只证明已发送。可用独立评审检测遗漏；成本和信息损失需随任务复杂度权衡，简单任务可以直接完成。

## 主动性从哪里来

- **外部与内部事件**：用户消息、任务完成、失败、审查结果、数据更新等触发 Chief 醒来判断。
- **定时触发**：按工作室政策配置目标巡检、日报或组织评估；明确时区、预算、停止条件和错过时的处理。事件与定时可并存。
- **记忆召回**：Chief 被唤醒后，根据目标、当前问题、相关角色、时间和失败检索可用记忆。召回本身通常需要正在运行的组件执行；记忆不会凭空唤醒已经停止的进程。
- **周期性回忆**：宿主的定时任务可唤醒 Chief，Chief 再查近期未完成事项、旧决定、待复核经验或逐渐过期的知识。可选随机抽样只作为寻找关联线索的方式，受预算、权限、去重和来源检查约束；不是制造新任务的理由。

一个召回结果只是一条候选依据，需检查时间、来源、适用范围和冲突；按价值与授权决定采取行动、等待或忽略。定时器和召回具体怎么配置要看宿主真实能力。

## 从一次需求到组织演化

目标最初可能只需要一个执行 session。交付质量需要独立判断时创建审查 session；一种问题持续积压时增加相应专业能力；并行不足时增开执行 session；长期需求稳定后才考虑长期 Bot。闲置时先暂停新 session 或保留待命，不把闲置视为失败。记录组织决策及其效果，定期复盘，但不自行扩大权限或预算。详见 [组织与汇报](08-organization.md) 和 [工作室演化案例](10-evolving-studio.md)。
