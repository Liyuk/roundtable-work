# Pages demo: deployment and contributor guide

Slice 3 of 4 of the Pages demo. This page describes how the static demo in `site/` is validated and published to GitHub Pages, how to preview it locally, what a maintainer must set up once, and how to roll back.

Status: the workflow is added by this change. Until a maintainer enables Pages (see [one-time repository setup](#one-time-repository-setup-by-a-human)) and a deployment has run from `main`, nothing is published, and the page's "implemented vs planned" table keeps calling the Pages deployment planned. Nothing here says the site is live.

## What is published, and what is not

Published: the three files in `site/`, and nothing else.

| File | Origin |
| --- | --- |
| `site/index.html` | Generated by `scripts/build-site.mjs` from [`scenario.json`](scenario.json) |
| `site/styles.css` | Hand-written |
| `site/app.js` | Hand-written, optional stepper for the walkthrough |

Not published: the rest of the repository (source, tests, `docs/`, local agent state, workflow files), any real issue, diff, log or host data, and anything that needs a backend. The demo is static and uses synthetic data only. It has no secrets and no network calls, and it cannot merge, deploy or run any privileged action. Deployment is started only by CI after a human has reviewed and merged a change.

`scripts/validate-site.mjs` enforces the boundary before every upload (see [validation](#validation)).

## How the workflow behaves

The workflow is [`.github/workflows/pages.yml`](../../.github/workflows/pages.yml).

| Event | Build and validate | Deploy |
| --- | --- | --- |
| Push to `main` (for example a merged PR) | Yes | Yes, after the build job succeeds |
| Pull request from a branch in this repository | Yes | Never |
| Pull request from a fork | Yes | Never |
| Manual run (`workflow_dispatch`) on `main` | Yes | Yes, after the build job succeeds |
| Manual run on any other branch | Yes | No: the deploy job requires `refs/heads/main` |

Safeguards in the workflow:

- Pull requests use the `pull_request` trigger only. The workflow never uses `pull_request_target`, never reads repository secrets, and runs only on GitHub-hosted runners.
- Permissions start at none. The build job gets `contents: read`. Only the deploy job gets `pages: write` and `id-token: write`, which `actions/deploy-pages` needs. Nothing gets `write-all`.
- The deploy job has `needs: build`, so a failing test, drift check or validation blocks publication.
- The deploy job uses the `github-pages` environment, so any protection rules set on that environment also apply.
- The deploy concurrency group is `pages` with cancellation off, so a deployment in flight is not cancelled. Pull request builds use a separate per-ref group, so they never queue behind a deployment.
- Checkout does not persist credentials. Only official `actions/*` actions are used, pinned to a major-version tag in the same style as `check.yml`. Dependabot proposes updates as ordinary reviewed PRs. No commit SHAs are pinned by hand.

What the build job runs, in order:

1. `npm ci`
2. `npm test` (unit tests plus `npm run check`, the Markdown link check)
3. `npm run build:site -- --check` (the committed `site/` must equal a fresh build)
4. `npm run validate:site` (artifact allowlist and content patterns)
5. Upload `site/` as the Pages artifact

## Local preview, validation and build

Requires the Node.js version in `.nvmrc`. No other dependency is needed to preview or validate; `npm ci` installs nothing extra for these scripts.

```
npm run preview:site
```

Serves `site/` on `127.0.0.1`, port 4173 by default (the script prints the exact address; open it in a browser). Set `PORT` to use another port, for example `PORT=8080 npm run preview:site`. Stop it with Ctrl+C. The server listens on the loopback address only, answers GET and HEAD only, serves only the files in `site/`, and refuses paths that try to leave that directory.

```
npm run build:site            # regenerate site/index.html from scenario.json
npm run build:site -- --check # exit 1 if site/ differs from a fresh build; writes nothing
npm run validate:site         # check what would be published
npm test                      # unit tests, then the Markdown link check
npm run check                 # the Markdown link check on its own
```

To change the page content, edit [`scenario.json`](scenario.json) (or the hand-written `site/styles.css` and `site/app.js`), run `npm run build:site`, then `npm test`, and commit the regenerated `site/index.html` with the change. The CI drift check fails if you forget.

### Runtime status output

Status is local by default: `node runtime/rtd.mjs status` writes text to standard output, and `--json` writes JSON there. To create an optional HTML file, use `node runtime/rtd.mjs status --html -o ./status.html`. Any status file written with `-o` or `--publish FILE` is scanned before writing; a privacy finding exits non-zero and leaves an existing destination unchanged. `--publish FILE` can be combined with `--json` or `--html` to choose the output format. Publishing fails closed when the scan rejects the rendered output.

If a maintainer separately chooses a Pages path, keep the status artifact in an isolated staging directory and publish only the reviewed status file through a separately configured Pages artifact. Do not copy runtime output into this demo's `site/` or enable Pages as part of local status generation. The default remains local, and passing the scan is a safety check rather than a substitute for review.

### Validation

`npm run validate:site` fails when:

- `site/` contains anything other than `index.html`, `styles.css` and `app.js` (extra files, subdirectories and symlinks all fail), or one of them is missing;
- a file contains an absolute web URL (either http or https scheme), a protocol-relative URL, a `file:` URL, or a root-absolute reference such as `href="/x"`;
- a file contains a local absolute path (for example a home directory), a GitHub token pattern, a private key header, a cloud access key pattern or an IPv4 address.

The messages name the file, line and rule, never the matched text. The check is a safety net, not proof that content is safe: reviewers still read the diff.

## One-time repository setup by a human

The workflow does not enable Pages, and the demo cannot deploy. A repository admin does this once:

1. Open Settings, then Pages. Under Build and deployment, set Source to **GitHub Actions**. Until then the deploy job fails at the Pages configuration step, which is the intended safe default.
2. Recommended hardening, in Settings, then Environments, then `github-pages` (GitHub creates it when Pages is first set up with Actions):
   - add **required reviewers**, so each deployment waits for a human to approve it;
   - under deployment branches, allow **`main` only** (a protected-branch rule or selected branch rule).
3. Check Settings, then Actions, then General, then Workflow permissions: leave the default as **read repository contents** permission. The workflow declares its own permissions and does not need a broader default.
4. Recommended: protect `main` so changes land only through reviewed PRs.

After the first deployment from `main`, the site address is shown on the deploy job and in the repository's Pages settings. Check the page in a browser before announcing it, and only then update any text that calls the deployment planned (that is a separate, reviewed change).

## Rollback

A bad page is fixed forward through the normal process. The preferred order:

1. **Revert the offending commit on `main` through a normal reviewed PR.** The merge triggers the workflow, which tests, builds, validates and deploys the reverted content. This is the only path that keeps `main` and the published site consistent.
2. **Redeploy manually if needed.** After the revert is on `main`, start the Pages workflow from the Actions tab with "Run workflow" on `main`. Re-running an older successful run on `main` redeploys that run's commit; use it only if you have confirmed that the commit is good, and note that stored artifacts expire, so an old run may have to rebuild or may not be re-runnable. Manual runs on other branches never deploy.
3. **Take the site down.** If the content must disappear while a fix is prepared, a repository admin can unpublish the Pages site in Settings, then Pages. This is a human action in the repository settings; the workflow cannot do it.

What can and cannot be undone:

- The published site can be replaced or unpublished. Browser caches, CDN caches and search engines may keep serving the old copy for a while; there is no way to force that, and no recovery time is guaranteed.
- Anything that was already copied, cached or archived by others cannot be pulled back. If sensitive data ever reaches a published page, treat it as exposed: rotate whatever it was, in addition to rolling back.
- Reverting changes the current site and the current branch. The git history, including the bad commit, remains.

## Troubleshooting

| Symptom | Likely cause and fix |
| --- | --- |
| `npm run build:site -- --check` fails | `site/` is out of date. Run `npm run build:site`, review the diff and commit it. |
| `npm run validate:site` fails | Read the file, line and rule in the message. Remove the external reference or the pattern; do not add files to the allowlist without review. |
| `npm test` fails on a link | `npm run check` reports a Markdown link whose target does not exist. Fix the relative path. |
| Deploy job fails at Pages configuration or deployment | The Pages source is probably not set to GitHub Actions yet. See the setup section. |
| Deploy job waits | The `github-pages` environment has required reviewers. A reviewer approves it in the run. |
| Deploy job is skipped | The run was a pull request or a manual run outside `main`. This is expected. |
| Preview does not start: port in use | Set a different port: `PORT=8080 npm run preview:site`. |
| The site looks old after a deployment | Caches. Reload without cache, wait, and check the deploy job's result. |

The workflow itself can only run on GitHub. Locally you can run every step it contains, but not the workflow file.

## Privacy and claims reminder

- Synthetic data only. Never add real issue content, diffs, logs, host paths, host names, addresses, user names or credentials to `scenario.json` or `site/`.
- Do not write that the system runs 24/7 or that recovery is guaranteed. The demo shows a bounded loop with human gates and checkpoints, and says what is planned versus implemented.
- Keep the page static: no backend, no secrets, no external requests.
- A human reviews and merges every change before it can be deployed.
- The first-line verdict contract used by the review step keeps its fixed wording wherever the page shows it. Do not translate or edit it.
