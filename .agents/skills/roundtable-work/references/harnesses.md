# Harness Interface and Adapters

A harness is the agent runtime that runs a role's session. This file describes the harness interface in the runtime, each built-in adapter and its declared capabilities, the degraded review path, and how to map host tools in a live session. Facts below come from `runtime/lib/harness.mjs`, `runtime/lib/agent-adapter.mjs`, and `runtime/lib/reviewer-session.mjs`, and from `runtime/harness.config.json`.

## Harness Interface

A harness is an object with this shape:

```text
{ name, capabilities: { subSession, writeFiles, invocation }, buildArgs({ sessionId, resume, prompt }) }
```

- `name`: the harness name used in `runtime/harness.config.json`.
- `capabilities.subSession`: whether the harness runs as a sub-session of the caller.
- `capabilities.writeFiles`: whether the harness can write files in the workspace.
- `capabilities.invocation`: how the harness is invoked: `bash-wrapped`, `exec`, or `in-process`.
- `buildArgs({ sessionId, resume, prompt })`: returns the process arguments, or `null` when nothing is spawned.

Registry and lookup:

- `HARNESSES` is the frozen registry of the three harnesses below.
- `selectHarness(name)` returns the harness, or throws `unknown harness: <name>` for an unknown name. Prototype names such as `toString` are rejected too (fail closed, using `Object.hasOwn`).
- `loadHarnessConfig` reads `runtime/harness.config.json`. Every role's harness name must be a known harness; an unknown name throws. `implementerRole` names the role that writes code.

Launching a process:

- `createAdapterLauncher({ adapter, command, env, spawnFn, proxySocket })` returns `launch({ workspace, sessionId, resume, prompt })`, which resolves to the exit code.
- The child process runs with `cwd` set to the workspace.
- `childEnv` strips every variable whose name starts with `GH_` or `GITHUB_` from the child environment, so role sessions never receive a GitHub write token. If `proxySocket` is set, `RT_GH_PROXY_SOCKET` is added.
- An `in-process` harness is refused with an error; it can never be launched as a process.

## Adapters

### `pi`

- Capabilities: `subSession: false`, `writeFiles: true`, `invocation: 'bash-wrapped'`.
- Arguments: `['--session-id', <id>, '-p', <prompt>]`.
- A separate `pi -p` process is a different session from the caller, so `subSession` is `false`.
- Verified: the `--session-id` and `-p` flags exist in `pi --help`.
- Not verified: that a second call with the same id continues the same conversation.

### `codex`

- Capabilities: `subSession: false`, `writeFiles: true`, `invocation: 'exec'`.
- Arguments for a new turn: `['exec', <prompt>]`. Arguments for a resumed turn: `['exec', 'resume', <id>, <prompt>]`.
- `codex exec` is a separate process, so `subSession` is `false`.
- Verified: the `exec` and `exec resume` subcommands and their flags exist in `codex exec --help` and `codex exec resume --help`.
- Not verified: `exec` assigns its own thread id. The `sessionId` generated by the runtime is not known to be codex's thread id, so resuming with it is unverified.

### `host-agent`

- Capabilities: `subSession: true`, `writeFiles: true`, `invocation: 'in-process'`.
- `buildArgs` returns `null`. The agent runs inside the host and spawns nothing.
- The runtime never launches it: `createAdapterLauncher` refuses in-process harnesses.

## Review Path and Degradation

Gate 1 review runs the reviewer as a separate OS process.

- The command is `RT_REVIEWER_COMMAND`, default `pi -p`. It is split on whitespace and spawned without a shell. The prompt is the last argument, and `--model <model>` is added when a model is routed.
- The reviewer runs read-only. `buildReviewerPrompt` tells it not to run tests and not to modify files. It judges the recorded Gate 0 summary, which is the test evidence.
- The verdict is the first line of the reply, exactly `Verdict: pass`, `Verdict: reject`, or `Verdict: block` (pass, reject, or block). These tokens are machine contract strings and must not be translated. Any other first line is treated as blocked. The legacy Chinese first lines `审查结论：通过`, `审查结论：打回`, and `审查结论：阻塞` are parse-only aliases; writers must not emit them.

Degraded path:

- If the reviewer binary cannot be found (`ENOENT`) and a single-session review callback is supplied, the review falls back to a degraded single-session review in the author's session.
- The result is labelled `independent: false` with `note: 'not independent'`. This label is required on every degraded review.
- Gates refuse a degraded result as a Gate 1 pass. A degraded review never counts as independent review.
- If no callback is supplied and the binary is missing, the launcher returns `REVIEWER_UNAVAILABLE`.

Read-only sandbox guidance:

- If the reviewer's sandbox is read-only, do not force tests inside it, and do not stall waiting for a writable sandbox.
- Rely on the recorded Gate 0 summary (test evidence), and still give a verdict on the first line, using the exact tokens above.
- Do not end the review silently. If the evidence is insufficient to judge, the verdict is `Verdict: block` with the reason in the rationale.

## Host Capability Mapping

Before starting, check the actual tools available in the current session. A tool named in this section is not supported until it has been invoked or its presence in the session's tool list has been confirmed. If a tool is not found, treat that capability as unsupported.

| Capability | Purpose | Claude Code (listed, not verified) | Codex (listed, not verified) |
| --- | --- | --- | --- |
| Create sub-session | Delegate execution and independent review | `Agent` (or `Task`) tool; `subagent_type` may select `rt-developer`, `rt-reviewer`, `rt-fixer`, `rt-researcher` from `.claude/agents/` | In-session collaboration tools such as `spawn_agent`; or `codex exec` for non-interactive execution |
| Receipt granularity | Record delegation events | Usually only started and completed | Depends on the tool |
| Send follow-up to existing sub-session | Fixes and target revisions | `SendMessage` (if available) | Tools such as `followup_task` |
| Wait for results | Collect delivery cards | Foreground calls return directly. Background runs (`run_in_background`) notify Chief's new turn; observed on desktop 2026-11-10, same application session only | Tools such as `wait_agent` |
| Wake up after turn ends | Continue without external prompting | Scheduled-task or timer tools (for example `CronCreate`, `/loop`) if present in the session | Not verified |
| Skill discovery | Load this skill | `.claude/skills/<name>/SKILL.md`, and `<user home>/.claude/skills/` | `.agents/skills/<name>/SKILL.md` |

Receipts: the host gives two receipts, started and completed. Record the rest as unverified (`sent+started` and `returned` only). Do not infer `delivered` or `acknowledged` from them.

When the harness has both application-level sessions (visible to the user, independently running) and in-process sub-agents, deliver delegation cards to sub-agents by default. Use application-level sessions only for tasks the user asked to run independently.

## Recording Method

Write one capability line in the continuation record or ticket during the first turn, for example:

```text
Host: Claude Code · sub-session: listed, not verified (Agent) · follow-up: listed, not verified (SendMessage) · wake-up after turn: not verified · evidence: session tool list
```

For each capability not personally invoked, write "listed but not verified". Do not write "supported" just because a document or this table names a tool.

## Strategies by Capability

- **Can create a sub-session and collect results**: the author and the reviewer use different sub-sessions. Chief reads only delivery cards and the necessary evidence.
- **The sub-agent's working directory differs from the workspace** (the session was opened in another repository): write absolute paths on the card. A harness's isolated working tree usually applies only to the session's own repository and does not replace workspace isolation.
- **Sub-sessions cannot communicate directly**: all communication goes through Chief: author → Chief → reviewer → Chief → author.
- **Can only wait in the foreground**: Chief waits and continues within the current turn. Tell the user that the session will not continue automatically after the turn ends.
- **No delegation capability**: one session executes sequentially. Mark the review as "self-check, not independent" (degraded; not independent).
- **Has post-turn wake-up capability**: set a wake-up only for a registered wait condition. State the purpose, interval, validity period, and stop conditions. Do not create timer tasks without authorization.
