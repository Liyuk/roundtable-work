# Runtime policy (host, unattended deployment)

> Maintained by the rt-loop deployer. Only narrows host privileges; never widens them. Do not write secrets here.

## External privacy (hard rule)

Do not write host-identifying information into issues, PRs, comments, commit messages, or repository files, including: IPs, hostnames, OS usernames, home-directory absolute paths, credentials, or secrets. Use placeholders in any outward text: `the host`, `$RT_HOME`, `<vps>`, `<host-runner>`. Local paths in this file are only for running on this machine; do not copy them to GitHub.

## Authorization

- Whose work may be accepted: GitHub intake: the scheduler `rt-sched.py` only claims open issues whose author is the user (__OWNER__) in repo __REPO__, and applies `rt:running` on the issue; it does not claim issues labelled `rt:owner`/`rt:hold`/`rt:blocked`/`rt:ask`/`rt:ready-to-merge`, issues whose title starts with `[Owner]`, epic issues, or issues whose dependencies (`Depends on #…`/`Blocked by #…`) are unmet
- May be done without asking: read the worktree; edit in this issue's dedicated worktree and `rt/<issue>-pi` branch; after a passing review, the Chief commits on the feature branch; run local tests and checks; `git push origin rt/<issue>-pi` (fast-forward only); `gh pr create` to open a PR (body includes `Closes #<issue>`, real checks, and leftover items); at most one explanatory comment on that issue or PR (for a delivery summary; ask/stop/claim/Gate results are published by the worker with real gh, and every comment carries a machine marker). Creating child issues, applying labels, and `gh pr ready` are done by the worker from files the Chief writes; the Chief cannot do them
- Must ask the user first (write DECISION=ask, do not do it yourself): release or deploy, enabling GitHub Pages, deleting data or branches, installing global dependencies or a third-party skill, changing the issue scope. **Merging is not in this list**: see "Auto-merge" below (done by the worker, not the Chief)
- Conversation and decision categories (closed list; line 2 of DECISION=ask must be one of these): `scope`, `credentials`, `destructive`, `direction` (there is no `merge`). `credentials|destructive` go straight to the owner; `scope|direction`, or a category not in the list, go to the decider (rt-decide) first, and if it can decide the owner is not disturbed; a scope question about "how to meet this issue's existing acceptance criteria" (needing to touch files outside the touch set, or a literal reading of the acceptance criteria that is unreliable on a shared host) is not a scope change: the decider decides directly to widen the touch set to meet the acceptance criteria (safety files still follow the safety-merge rule), or to take an isolated, deterministic reading and record it in the PR
- Forbidden (Chief and every sub-session): push to main/master; force push (do not rebase an already-pushed branch either; sync main with `git merge origin/main`); delete a remote branch; `gh pr merge`, close/reopen an issue, `gh api` write operations; read, print, or modify any credential/secret (including `.github` secrets, `~/.pi/agent/auth.json`, `~/.codex/auth.json`, and the gh token); write paths outside the worktree (temporary files outside `.roundtable/scratch/` may go under /tmp)

## Auto-merge (owner decision, executed by the worker; the Chief does not take part)

- Merge only when every prerequisite is met: Gate 0 (deterministic) passed; Gate 1 = the review-tier independent review gave `Verdict: pass` on **the tree of the current head** (if none exists, the worker runs `rt-delegate reviewer` itself; reject → a Gate fix round; unavailable → retry once, and if still unavailable only label `rt:ready-to-merge` and do not merge); for a high-risk diff, Gate 2 has **no "in-scope for this issue and high/critical" findings** (when RT_LENIENT=1, only "in-scope critical with a concrete trigger" counts; high and below are recorded on a PR comment, with no issue opened; after the review budget is used, a Gate 1 reject is not a blocker, and the comments go into the PR body) (out-of-scope findings, or medium/low findings, are recorded on a PR comment only, do not block this merge, and **do not open a follow-up issue** (owner 2026-11-12, RT_AUTO_FOLLOWUPS=0; set to 1 to restore auto-opening issues)); the PR's required CI is all green (`gh pr checks --watch --required`, up to RT_CI_TIMEOUT; red/timeout follows the Gate-failure fix path; never merge a red PR).
- Merge only through `bin/rt-merge <pr>` (the only place that calls `gh pr merge --squash`; do not use `--admin`/`--auto`): it requires `RT_MERGE_STEP=1` and `wt/<n>/.roundtable/state/gates.json` all green with a head that matches the PR, and it re-checks that the PR is still open, not draft (run `gh pr ready` first), mergeable, CI green, has a passing `<!-- rt:gates -->` comment, and the body contains `Closes #<n>`; it records `state/merges.log` and applies `rt:merged`.
- Safety files (`.githooks/`, `pre-push`, `bin/gh`, `limits`, `policy`, `runtime/lib/guard*`, `.github/workflows/`, `scripts/check.mjs`): need the decider `DECIDE: resolve` with `APPROVE-MERGE` in the text, and a `<!-- rt:opus-merge -->` comment on the PR first; otherwise only label `rt:ready-to-merge`, leave it for the owner, and explain why.
- Coordination: re-read a PR's status before merging or operating on it, and skip if it is already merged or closed; only handle PRs on `rt/<n>-*` branches; do not touch PRs in `RT_HANDS_OFF_PRS`. After a prerequisite PR merges, a stacked branch is updated with `git merge origin/main` plus a normal push (no force push); on conflict, abort and wake the Chief.
- If CI on main goes red after a merge and the head commit is an auto-merge product → the scheduler automatically opens an `rt/revert-<sha7>` revert PR, merges it once green, and opens a new `type:bug` `rt:self` issue; while main is red, new claims and merges are paused.

## Budgets and stop conditions

- Maximum attempts per assignment: 2
- Review rejects: at most 2 rounds. When RT_LENIENT=1 (owner 2026-11-12 lenient merge mode, currently on), after 2 rounds do not stop and do not ask: if Gate 0 (tests, privacy) passed, commit, push, and open/update the PR, put unresolved review comments in the PR body under `## Outstanding review findings (non-blocking, owner lenient mode)`, and DECISION=done; after the review budget is used, the worker treats a Gate 1 reject as non-blocking and merges once CI is green. When RT_LENIENT=0: after 2 rounds, DECISION=ask for the user's decision
- Consecutive no-progress turns: at most 2 → `stop`
- Concurrent writers of the same file: 1 (each issue has its own worktree, so only one writer at a time; each issue has one `locks/<n>.lock` flock); at most __WORKERS__ issues in parallel (RT_WORKERS); issues in the same series (the first square-bracket prefix in the title, e.g. Pages, RT, I18N) are mutually exclusive; two issues with a dependency are mutually exclusive
- Decider-call budget: RT_DECIDE_MAX=2 per issue; regular Gate fix rounds at most 2 (`fix_n` / FIX_MAX). If gates still fail after 2 rounds, do not go straight to `rt:blocked`: the worker has the decider tier (fixer role, edit/write allowed) fix 1 more round (`opus_fix_n`, cap 1), fixing only blockers and adding regression tests, without expanding scope, then re-runs Gate 0/1/2. If the only remaining failures are in-scope high/critical Gate 2 findings, and Gate 0 and Gate 1 already passed, it makes 1 more read-only decider-tier call (security role) for an exploitability judgment (`opus_exploit_n`, cap 1): each blocker is `exploitable` or `not-exploitable` plus a reason. All `not-exploitable` → downgrade and release (record the decider's reasons on a PR comment only, no issue), treat Gate 2 as passed, and auto-merge as usual if Gate 0, Gate 1, and CI also passed, leaving a downgrade-release note on the PR. Any `exploitable`, or unparseable decider output: fail closed, label `rt:blocked`. This release does not apply when Gate 0 or Gate 1 has not passed; those stay blocked. The safety-file merge rule (`APPROVE-MERGE`) is unchanged. The counters above persist in `state/issues/<n>.json` across restarts and are cleared together after an owner reply; the safety-file merge decision is counted separately (at most 2 per issue)
- Per issue: the Chief is woken at most 4 times, each wake at most 60 minutes; each sub-session at most 25 minutes
- A reviewer sub-session with a non-zero exit / timeout / empty output = "review unavailable", not a reject, and it does not consume a development attempt; the review may be dispatched once more

## Execution routing

| Kind of work | How it is run | Tier (concrete models: see "Routing facts for this turn") | Verified |
| --- | --- | --- | --- |
| Chief (triage, orchestration, commit, PR) | the worker wakes `bin/rt-agent chief` each time (the same issue continues the same session: pi `--continue` / codex `exec resume`; the full prompt is still fed every time) | development tier (chief) | verified |
| Implementation / fix / research | `rt-delegate developer\|fixer\|researcher <card> <worktree>` (independent session process, via `bin/rt-agent`) | development tier (developer/fixer/researcher) | not verified |
| Gate 1 independent review / verification (including a review the worker runs itself) | `rt-delegate reviewer <card> <worktree>` (another independent session process; acceptance-criteria-first: pass when the acceptance criteria are met and tests pass; reject only when an acceptance criterion is unmet or there is a high-risk defect with a concrete trigger; everything else goes in notes; security is Gate 2; a verdict is discarded if the worktree changes during review) | review tier (reviewer; owner 2026-11-12: review is stronger than development; this is allowed and does not count as the Chief calling the decider tier) | not verified |
| Questions that cannot be decided alone (deadlock/no progress, gate disagreement, ambiguous triage, before disturbing the owner, safety-file merge) | `bin/rt-decide` (`bin/rt-agent decider`, read-only; decides only, does not implement or review) | decider tier (decider) | not verified |
| Threat-model rewrite (only when SUPERVISOR.md / an owner reply explicitly asks for a complete threat model and then a full rewrite) | the worker first uses the decider tier (security role) to produce the threat model (read-only, written to `.roundtable/state/threat-model.md`), then wakes the Chief to rewrite the in-scope files against that model and add regression tests | decider tier (security) produces the model + development/review tiers implement and review | not verified |
| Escalation after the regular 2 fix rounds still fail | the worker first has the decider tier (fixer) fix 1 round itself (edit/write allowed); if only Gate 2 still blocks and Gate 0/1 passed, it then makes a read-only exploitability judgment and downgrade-releases if nothing is exploitable | decider tier (fixer / security) | not verified |
| Gate 0 | `bin/rt-gate0` (deterministic, no model) | — | — |
| Gate 2 cross-check (high-risk diffs only) | `bin/rt-xcheck` (read-only session); must state severity and whether the finding is in scope; only in-scope high/critical findings with a concrete trigger (critical only in lenient mode) fail the gate; everything else is recorded on a PR comment, with no issue opened | review tier (reviewer) | not verified |

The only source of model routing is `config.env`. `bin/rt-agent` generates a "Routing facts for this turn" block at each role start and injects it into the system prompt (`bin/rt-agent --routing-facts` to inspect). When DeepSeek returns insufficient balance, roles automatically switch to `RT_NOFUNDS_MODEL`, which is also written into the routing facts. The `opus` in old labels (for example `rt:opus-merge`, `opus_fix_n`) is only a name and refers to the decider tier.

## Improvement targeting (autonomy benchmark, owner 2026-11-16)

- The benchmark `docs/autonomy-benchmark.md` (U unsupervised, L self-loop, I self-iteration, D self-decision; sub-metrics U1..., L1..., I1..., D1...) is the yardstick for all improvement work.
- When the Chief sources or prioritizes self-sourced issues, it targets the lowest-level sub-metric first and writes `Benchmark target: <id> (current level N, value V) -> expected delta: <...>` in the issue body. Issues without a target need a one-line reason.
- A regression flagged by `rt-bench` (sub-metric level drop on the rolling window) gets one self issue targeting that sub-metric (update the existing one if open, no duplicates).

## Triggers and wakes

- User messages: not online; write DECISION=ask when a human is needed
- Sub-task completion notices: rt-delegate is a foreground synchronous call; return means completion
- External events (GitHub, CI, webhook): not enabled (the webhook was removed)
- Wake after a turn: each issue's `rt-work.sh` reads `.roundtable/state/DECISION`: continue/wait → wake again (wait interval 5 minutes); done → Gate 0/1/2 → label `rt:ready-to-merge` → wait for CI → auto-merge (see above); ask → decision-category routing (see above); stop/no progress/wake budget exhausted → ask the decider once first, otherwise `rt:blocked`; decompose → create `rt:self` + `rt:go` child issues and `rt:hold` (the scheduler only claims `rt:self`/`rt:followup` issues that also have `rt:go`); out-of-scope → comment + `rt:blocked` (do not close)
- An owner reply on the issue is automatically written by the scheduler into `SUPERVISOR.md`, and the issue is resumed (`rt:ask`/`rt:blocked`/a terminal state can all resume)
